Views and Viewpoints

•   Idea central: la arquitectura de un sistema es demasiado compleja para describirla desde un único
    ángulo. Por eso se documenta mediante vistas (views) y puntos de vista (viewpoints).

•   View: una representación de la arquitectura, hecha con un objetivo y para un grupo de interés (ej. vista
    lógica, vista de procesos, vista de despliegue).

•   Viewpoint: la plantilla o “receta” que deﬁne cómo construir una vista: qué notación usar, qué elementos
    incluir, para quién está pensada.


La vista lógica es un view, y el punto de vista lógico (que dice qué diagramas UML usar, qué mostrar, etc.) es
el viewpoint.
Ejemplo:
  ● View: “diagrama de clases del sistema de ventas”
  ● Viewpoint: “uso UML, muestro clases de dominio, omito infraestructura, target: devs”

===== PAGINA 7 =====

Views and Beyond

•    Es un método práctico para documentar arquitecturas usando el enfoque de views and viewpoints.

•    Propone tres categorías de vistas:
    • Módulo: cómo se organiza el software en unidades de código.
    • Componente y conector: cómo interactúan los elementos en tiempo de ejecución.
    • Asignación: cómo se mapean esos elementos al hardware, equipos o procesos.

•    El “beyond” del título señala que además de vistas, hay que incluir información adicional: escenarios,
     decisiones arquitectónicas, justiﬁcaciones, etc.

                  Es como un “manual práctico” para aplicar la idea de views and viewpoints.

IEEE 1471 (ahora ISO/IEC/IEEE 42010)

•   IEEE 1471: reemplazado por 42010 en 20211

•   Fue el primer estándar formal de descripción de arquitectura de software (año 2000).

•   Introdujo oﬁcialmente los conceptos de views y viewpoints.

•   Objetivo: que las arquitecturas sean documentadas de forma consistente y comprensible para distintos
    stakeholders.

•   Evolucionó al estándar actual ISO/IEC/IEEE 42010, que amplía y formaliza la práctica.

•   ISO/IEC/IEEE 42010:2011: primer versión.

•   ISO/IEC/IEEE 42010:2022: segunda versión y estándar vigente.

Vista Lógica y Vista de Procesos

Vista lógica
• Pregunta: ¿Cómo está organizado el sistema desde el punto de vista de las funcionalidades?
• Foco: Estructura del software y sus elementos estáticos.
• Contenido típico:
  • Clases, objetos, módulos, capas.
  • Relaciones de herencia, composición, asociaciones.
  • Diagramas UML de clases o diagramas de componentes.

Vista de procesos
• Pregunta: ¿Cómo se comporta el sistema en tiempo de ejecución?
• Foco: Aspectos dinámicos: concurrencia, comunicación, sincronización, rendimiento.
• Contenido típico:
  • Procesos, hilos, tareas concurrentes.
  • Mensajes, colas, comunicación entre procesos.
  • Diagramas UML de secuencia, de actividades, o de comunicación.

===== PAGINA 15 =====

Vistas de Desarrollo y Vista Física

Vista de desarrollo (o de implementación)
• Pregunta: ¿Cómo se organiza el software en el entorno de desarrollo?
• Foco: Estructura estática a nivel de módulos, componentes y paquetes, pensada para los desarrolladores.
• Contenido típico:
  • Paquetes, bibliotecas, frameworks.
  • Organización en repositorios o directorios.
  • Dependencias entre módulos.
  • Diagramas UML de componentes o de paquetes.

Vista física (o de despliegue)
• Pregunta: ¿Dónde y cómo se ejecuta el sistema en la infraestructura física?
• Foco: Asignación del software al hardware y redes.
• Contenido típico:
  • Nodos, servidores, contenedores, dispositivos.
  • Topología de red, balanceadores de carga.
  • Diagramas UML de despliegue.                                                                      15

===== PAGINA 16 =====

Vista de Escenarios

Vista de escenarios (o casos de uso)
• Pregunta: ¿Qué comportamientos clave validan que las otras vistas funcionan en conjunto?
• Foco: Historias concretas de uso que atraviesan las demás vistas.
• Contenido típico:
  • Casos de uso detallados.
  • Diagramas UML de casos de uso o secuencia.
  • Narrativas de interacción usuario–sistema.

Dataﬂow en modo batch secuencial

Compiladores clásicos (ej. GCC, Clang, JavaC)
• Pipeline secuencial: Análisis léxico (scanner) → Análisis
  sintáctico (parser) → Análisis semántico → Optimización
  → Generación de código.
• Cada fase consume el output de la anterior, de
  manera estrictamente secuencial

 - Problema: procesar grandes volúmenes de datos
    oﬄine
 - Cómo: etapas una detrás de otra
 - Cuándo usar:
       - ETL
       - procesamiento nocturno
       - pipelines donde no importa la latencia

 - Trade-oﬀ: simple pero lento (alta latencia)                26

===== PAGINA 27 =====

Dataﬂow en modo Pipes & Filters

Renderizado y edición de imágenes / vídeo
• Los editores aplican transformaciones encadenadas:
   Imagen → Filtro de contraste → Filtro de nitidez →
   Reducción de ruido → Guardado.
• En algunos programas, los ﬁltros son “streaming”:
   producen resultados parciales visibles mientras
   procesan.

 - Problema: procesar datos en ﬂujo continuo
 - Cómo: ﬁltros independientes conectados
 - Cuándo usar:
       - streaming
       - sistemas que requieren paralelismo
       - Apache Camel, Spring Integration

 - Trade-oﬀ: más ﬂexible, más complejo de coordinar     27

Dataﬂow en modo Hierarchical Layers

Protocolos de red (modelo OSI o TCP/IP)
• El clásico ejemplo de capas jerárquicas:
   Aplicación → Transporte → Red → Enlace → Física.
• Los datos bajan capa por capa, cada una agrega
   su header o transforma la información, y luego
   suben en el receptor deshaciendo las
   transformaciones.

 - Problema: organizar complejidad
 - Cómo: cada capa abstrae a la inferior
 - Cuándo usar:
       - sistemas grandes
       - arquitecturas enterprise
       - separación de responsabilidades
 - Trade-oﬀ: claridad vs posible impacto en
performance                                           28

Cómo elegir un estilo Dataﬂow
- ¿Tengo datos en lotes grandes? → Batch. Palabra clave: “volumen”
      - Sistemas de facturación (SAP, sistemas bancarios)
      - Liquidaciones, cierres diarios, cálculo de intereses: todo corre en batch nocturno.
      - Motores de recomendación oﬄine (ej. Netﬂix en parte de su pipeline)
- ¿Tengo ﬂujo continuo? → Pipes & Filters. Palabra clave: “ﬂujo”
      - Apache Kafka:
             - Filters: Los servicios o aplicaciones de procesamiento de streams que leen un mensaje, realizan
             una operación especíﬁca (validar, transformar, enriquecer o ﬁltrar) y escriben el resultado.
             - Pipes: Son los topics. Transportan los ﬂujos de mensajes de un ﬁltro a otro de forma desacoplada
             y persistente
- ¿Necesito organizar el sistema? → Capas. Palabra clave: “organización”
      - Hardware → kernel → servicios → aplicaciones.
      - Aplicaciones web típicas (por ejemplo con Django o Spring Framework)
      - Android: Framework → runtime → kernel → hardware

===== PAGINA 37 =====

Aplicaciones de usuario ﬁnales basadas en Broker

Plataformas de mensajería instantánea
• WhatsApp, Telegram, Slack, Discord: Los mensajes no van directo de usuario a usuario, pasan por
    brokers (servidores intermedios) que los enrutan, almacenan temporalmente, y entregan según
    disponibilidad.

Aplicaciones de delivery
• Uber, Rappi, PedidosYa: El broker aquí conecta pasajeros con conductores, o usuarios con repartidores.
    La app del cliente hace la solicitud 🡪 broker central recibe 🡪 busca un proveedor disponible 🡪 reenvía la
    tarea.

Servicios de correo electrónico
• Gmail, Outlook, Yahoo Mail: El broker de mensajería (SMTP/IMAP servers, colas internas) enruta mails
   entre dominios y usuarios.

Forwarder–Receiver

Peers: Son los componentes de la aplicación que necesitan comunicarse. No saben cómo viaja la
información, solo invocan al Forwarder para enviar y escuchan al Receiver para recibir.

Forwarder: Se encarga de recibir el mensaje del Peer de origen, transformar los datos a un formato apto
para la red (serialización) y enviarlos a través del canal de comunicación.

Receiver: Se encarga de escuchar el canal de comunicación, recibir los bytes binarios, transformarlos de
vuelta a un formato que el Peer de destino entienda (deserialización) y entregárselos.



Problema que resuelve: transparencia en sistemas distribuidos para comunicación directa

Cierre

●   Arquitectura de software = vistas + estilos
●   Vistas: Cómo describir el sistema
     ○ Diferentes perspectivas
     ○ Cada una responde a una pregunta distinta
     ○ Ejemplo: lógica, procesos, desarrollo, física, escenarios (casos de uso)
●   Estilos arquitectónicos: Cómo diseñar el sistema
     ○ Conjunto de decisiones de alto nivel
     ○ Restringen y guían el diseño
     ○ Ejemplo: layers, pipes & ﬁlters, broker, pub-sub
●   Mismo sistema
     ○ Distintas preguntas → distintas vistas
     ○ Distintas decisiones → distintos diseño
